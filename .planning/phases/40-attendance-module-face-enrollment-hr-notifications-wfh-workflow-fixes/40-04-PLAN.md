# Plan 40-04: WFH HR/Manager Notification Delivery & Notification Module Audit

**Phase:** Phase 40: Attendance Module — Face Enrollment, HR Notifications & WFH Workflow Fixes  
**Plan ID:** 40-04  
**Target:** WFH Notification Flow, Approval Chain Recipient Resolution & Navigation Links  
**Requirement Reference:** Sections 4 & 5 ("WFH Application — HR Notification Not Triggered" & "Complete Notifications Module Audit")

---

## 1. Goal & Objectives
Audit and resolve the complete Work From Home (WFH) notification lifecycle:
- When an employee submits a WFH request:
  - Both the employee's **Reporting Manager** (first-line reviewer) AND authorized **HR Managers & Super Admins** must be identified and notified.
  - The notification must include: Employee Name, Employee Code, Department, and requested WFH date.
  - The notification link must navigate directly to the WFH tab (`/attendance/team?tab=wfh`), ensuring instant inspection without manual navigation.
- When an approver decides (approves/rejects) the WFH request:
  - The applicant employee must be notified of the decision with link `/attendance/my?tab=wfh`.
- Audit the centralized `notify.service.js` to ensure in-app persistence, unread counter increments, and Socket.io emission work reliably.

---

## 2. File Level Changes

### 1. `backend/src/modules/attendance/attendance.service.js`
- In `getApprovalNotificationRecipients(applicantEmp)`:
  - Query manager's `userId` from `applicantEmp.managerId`.
  - Query all active users with role `Super Admin` or `HR Manager` (supporting both ObjectId references and string role fallbacks).
  - Deduplicate recipient list into an array of valid ObjectIds.
  - Exclude applicant's own `userId` so applicants do not receive submission notifications intended for management.
- In `applyWFH`:
  - Format notification title and body:
    - **Title:** `New WFH Request`
    - **Body:** `${applicantEmp.name} (${applicantEmp.employeeCode || 'Emp'}) has submitted a Work From Home request for ${formattedDate}. Please review the application.`
    - **Link:** `/attendance/team?tab=wfh`
  - Await `notify(recipientUserIds, payload)` or handle with structured error logging.
- In `decideWFH`:
  - Update decision notification link: `/attendance/my?tab=wfh`.
  - Notification body: `Your Work From Home request for ${formattedDate} has been ${decision} by ${actorName}.`.

### 2. `frontend/src/features/attendance/pages/TeamAttendancePage.jsx`
- Verify that when the page is loaded with `?tab=wfh`, `activeTab` automatically switches to `'wfh'`.
- Ensure WFH table and cards query runs immediately without requiring tab re-clicking.

### 3. Centralized Notification Audit & Socket.io Verification
- Audit `notify.service.js`:
  - Confirm `attendance` type maps to `module: 'attendance'`.
  - Confirm `adminNotifSetting` lookup fallbacks do not disable in-app notifications.
  - Confirm `emitToUser(notif.userId, 'notification:new', ...)` broadcasts to user's personal room.

---

## 3. Verification Criteria
1. Employee submits valid WFH request for tomorrow $\rightarrow$ Request saved in DB with status `pending`.
2. Notification record is created for Reporting Manager, HR Manager, and Super Admin.
3. Notification links to `/attendance/team?tab=wfh`.
4. Manager clicks notification $\rightarrow$ `TeamAttendancePage` opens directly on the WFH tab.
5. Manager approves/rejects WFH $\rightarrow$ Applicant employee receives notification with link to `/attendance/my?tab=wfh`.
