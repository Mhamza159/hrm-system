# Plan 09-03: Resume Buffer Hash Caching & Verification Hardening

## Objective
Implement SHA-256 buffer hash caching to eliminate redundant LLM API invocations during candidate re-screening, harden the system against prompt injections contained within actual extracted PDF/DOCX bodies, and expose the active AI provider/engine tag in the candidate inspection drawer.

---

## Tasks

### 1. SHA-256 Buffer Caching Engine (`backend/src/services/ai.service.js` & `recruitment.service.js`)
- Compute a SHA-256 hash of the uploaded document buffer or normalized text string.
- Check Redis (`recruitment:cv_parse:${hash}`) or in-memory LRU cache before invoking external LLM APIs.
- On cache hit: Return the parsed profile instantly (0ms latency, $0 token cost).
- On cache miss: Invoke LLM, cache the resulting structured JSON with a 7-day TTL (`604800` seconds).
- In `Candidate` model, record `aiProviderUsed` (`Gemini`, `OpenAI`, `Cached`, `Heuristic`).

### 2. Frontend Inspection Indicator (`frontend/src/features/recruitment/components/CandidateDetailModal.jsx`)
- In the Candidate Profile inspection drawer, display an AI Provider badge (e.g. `Engine: Gemini 2.5 Flash` or `Engine: OpenAI gpt-4o-mini`).
- Show whether the screening result was freshly generated or served from verified cache.

### 3. Security Stress & End-to-End Verification (`backend/tests/m15.recruitment.security.test.js`)
- Update Vector 6 (AI Prompt Injection Resistance) to test actual binary PDF documents containing embedded prompt injection vectors.
- Verify that cache hits return identical parsed profiles without making outbound network requests.
- Run complete test suite (`m15.recruitment.test.js`, `m15.recruitment.security.test.js`, `m15.documentParser.test.js`, `m15.multiProvider.test.js`).
- Verify production frontend build compiles cleanly with zero errors.
