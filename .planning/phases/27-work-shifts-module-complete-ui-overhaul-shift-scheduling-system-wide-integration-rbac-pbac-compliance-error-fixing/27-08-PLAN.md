## 2. Step-by-Step Implementation

### Step 1: Add RTK Query Archival Endpoints in `departmentsApi.js`
- Endpoints:
  ```javascript
  getArchivedShifts: builder.query({
    query: (params) => ({
      url: '/shifts/archived',
      params
    }),
    providesTags: ['Shifts', { type: 'Shifts', id: 'ARCHIVED' }]
  }),
  archiveShift: builder.mutation({
    query: (id) => ({
      url: `/shifts/${id}/archive`,
      method: 'PATCH'
    }),
    invalidatesTags: ['Shifts']
  }),
  restoreShift: builder.mutation({
    query: (id) => ({
      url: `/shifts/${id}/restore`,
      method: 'PATCH'
    }),
    invalidatesTags: ['Shifts']
  }),
  permanentDeleteShift: builder.mutation({
    query: (id) => ({
      url: `/shifts/${id}/permanent`,
      method: 'DELETE'
    }),
    invalidatesTags: ['Shifts']
  })
  ```

### Step 2: Build Archival Modals
- **`ShiftArchiveModal.jsx`**:
  - Explains that archiving moves the shift out of active scheduling and prevents assigning it to new employees.
  - Warns if active employees are currently assigned, noting that existing staff will keep their schedule until reassigned.
  - Amber confirmation button.
- **`ShiftRestoreModal.jsx`**:
  - Re-activates shift back to the active directory.
  - Confirms no code conflicts exist.
  - Emerald restore button.
- **`ShiftPermanentDeleteModal.jsx`**:
  - **NON-NEGOTIABLE GUARD**:
    - If `shift.headcount > 0`:
      - Red/Rose alert box: *"Cannot permanently delete shift because X employee(s) are currently assigned to it. Reassign all staff first."*
      - Delete button is strictly **DISABLED**.
    - If `shift.headcount === 0`:
      - Warning that permanent deletion removes the record from the database.
      - Requires typing the uppercase shift code to confirm.
      - Destructive Rose "Permanently Delete Shift" button.

### Step 3: Build `ArchivedShiftList.jsx`
- Dedicated high-density table for archived shifts.
- Columns: Shift Name & Code, Type, Timing & Overnight pill, Archived At date, Archived By user, Assigned Staff (if any), Actions (`Restore`, `Permanent Delete`, `Inspect`).
- Search and pagination controls.

### Step 4: Write Automated Vitest E2E Test Suite (`backend/tests/shifts.overhaul.e2e.test.js`)
- Author comprehensive E2E tests validating:
  1. `POST /api/v1/shifts`: Creation of standard, flexible, and night cross-midnight shifts (`isCrossMidnight: true`).
  2. Timing calculation validations: Rejection of break minutes $\ge$ total shift duration.
  3. `GET /api/v1/shifts/stats`: 7 live KPI counters matching real database counts.
  4. `GET /api/v1/shifts/analytics`: Type distributions and day/night ratios.
  5. `GET /api/v1/shifts`: Querying active shifts with headcount calculation.
  6. `POST /api/v1/shifts/:id/assign`: Bulk assignment of employees to shift and capacity enforcement.
  7. `GET /api/v1/shifts/:id/employees`: Paginated and searched assigned staff roster.
  8. `PATCH /api/v1/shifts/:id/archive`: Archival lifecycle and removal from active listing.
  9. Cross-module employee guard: Rejection of employee creation/update with archived `shiftId`.
  10. `PATCH /api/v1/shifts/:id/restore`: Restoring shift with duplicate code conflict checks.
  11. **Employee Assignment Restriction Guard**:
      - Attempting `DELETE /api/v1/shifts/:id/permanent` on a shift with $\ge 1$ assigned employee MUST return HTTP 400.
      - Reassigning employees to unblock.
      - Successful permanent deletion once headcount reaches 0.
  12. RBAC/PBAC verification: Permission checks for `org.view` and `org.manage`.
