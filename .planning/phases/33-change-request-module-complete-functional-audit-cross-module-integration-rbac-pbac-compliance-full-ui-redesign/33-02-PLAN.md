# Plan 33-02: Backend Change Request APIs, Multi-Tier Approval Chain, Scoped PBAC & Audit/Notification Integration

## Objective
Establish a complete RESTful API suite for Change Requests with strict RBAC/PBAC data scoping, Super Admin escalation protection, real-time notifications, and immutable audit log generation. Register dedicated `change_request.*` permissions, enforce department and team boundary isolation, provide rich aggregation metrics for dashboard analytics, and build secure attachment upload handling.

## Tasks
1. **RBAC & PBAC Permissions Catalogue Registration (`backend/src/shared/permissions.js`)**:
   - Register dedicated permissions for Change Requests:
     - `change_request.view`: Scopes `own`, `team`, `department`, `all`.
     - `change_request.create`: Scope `own`.
     - `change_request.edit`: Scope `own`.
     - `change_request.approve`: Scopes `department`, `all`.
     - `change_request.delete`: Scopes `own`, `all`.
   - Update `role.model.js` seed and permission matrix defaults so Super Admin and HR Manager have full approval authority, Department Managers have department-scoped approval, and Employees have self-service access.

2. **REST Endpoints & Controller Implementation (`backend/src/modules/employees/changeRequest.routes.js`, `employee.controller.js`)**:
   - `GET /api/v1/change-requests`: Scoped list with filters (`status`, `category`, `departmentId`, `search`, `page`, `limit`). Applies `applyDataScope('change_request.view')` filtering requests by employee department or team.
   - `GET /api/v1/change-requests/stats`: Returns KPI counts (`total`, `pending`, `under_review`, `approved`, `rejected`, `returned`, `myPendingAction`), category breakdown, and 6-month trends.
   - `GET /api/v1/change-requests/my`: Self-service endpoint for employees to fetch their own change requests with full timeline.
   - `GET /api/v1/change-requests/:id`: Deep inspection endpoint populating `employeeId`, `requestedBy`, `decidedBy`, `assignedTo`, `departmentId`, `designationId`.
   - `POST /api/v1/change-requests`: Create new change request with Zod payload validation, supporting document URLs, and priority.
   - `PATCH /api/v1/change-requests/:id/decide`: Approve or Reject with decision notes. Enforces `assertSuperAdminIfApplicantIsHR`.
   - `PATCH /api/v1/change-requests/:id/return`: Return request for employee revision with mandatory notes.
   - `PATCH /api/v1/change-requests/:id/cancel`: Requester self-cancellation.
   - `POST /api/v1/change-requests/upload`: Secure attachment upload via Multer (PDF, PNG, JPG, max 5MB).

3. **Audit Log & Real-Time Notification Integration**:
   - Integrate `AuditService.log` for all events:
     - `change_request.created` (category `DATA_CHANGE`, severity `LOW`)
     - `change_request.approved` (category `DATA_CHANGE`, severity `MEDIUM`, before & after snapshots)
     - `change_request.rejected` (category `ADMINISTRATIVE`, severity `MEDIUM`)
     - `change_request.returned` (category `ADMINISTRATIVE`, severity `LOW`)
     - `change_request.cancelled` (category `DATA_CHANGE`, severity `LOW`)
   - Dispatch multi-channel notifications via `notification.service.js` and Socket.io:
     - On submission: Notify HR Managers (or Super Admin if applicant is HR).
     - On decision / return: Notify requesting employee with actionable direct link.

## Verification Criteria
- Non-admin users cannot query or inspect change requests outside their authorized PBAC scope.
- HR staff submitting requests cannot approve their own changes; Super Admin escalation is strictly enforced.
- Every state transition produces an immutable audit record and dispatches a notification.
- Attachment uploads strictly enforce MIME types and size boundaries.
