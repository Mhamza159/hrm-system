## Core Roles Definition Alignment (`docs/FRD.md` Section 11)
1. **Super Admin**:
   - Master executive administrator with `manage:all` across `scope: 'all'`.
   - `isSystem: true` flag. Immune to rename, deletion, or permission reduction.
2. **HR Manager**:
   - Company-wide management rights (`scope: 'all'`) for Core HR, Employees, Attendance, Leaves, Payroll, Reports, Settings, Policies, and Announcements.
   - Restricted from authoring custom system roles or altering Super Admin permissions. Can assign existing roles to staff (`grant ⊆ actor.permissions`).
3. **Department Manager**:
   - Scoped operational rights (`scope: 'team'` and `scope: 'department'`).
   - Manages team leaves, team attendance, expense claims, loans recommendation, and direct subordinates.
   - Sensitive financial fields (`salary`, `bankAccount`, `cnic`) strictly masked and forbidden.
   - Supports approval delegation to peer managers (`POST /api/v1/delegations`).
4. **Employee**:
   - Self-service rights (`scope: 'own'`).
   - Mark attendance, view own timesheets, apply for leave, submit claims/loans, view own payslips, manage profile, participate in surveys/feedback.

## Detailed Implementation Tasks
- [ ] **Task 1: Role Schema Hardening (`role.model.js`)**:
  - Add `isActive` (Boolean, default `true`), `slug` (String, unique, lowercase), and compound indexes on `{ isSystem: 1, isDeleted: 1, isActive: 1 }`.
  - Validate that permissions array conforms to Zod/Mongoose schema with mandatory `action`, `subject`, and valid `scope`.
- [ ] **Task 2: Seed File Alignment & Idempotence (`roles.seed.js`)**:
  - Update `CORE_ROLES_DEFINITIONS` to reflect the comprehensive permission list from Plan 28-01 for all 4 roles.
  - Implement atomic upsert logic ensuring running `npm run seed` updates missing permissions on core roles without overwriting custom roles or generating duplicate key collisions.
- [ ] **Task 3: Backend Metrics & Analytics Endpoints**:
  - `GET /api/v1/roles/stats`: Aggregates:
    - `totalRoles`: Total non-deleted roles.
    - `activeRoles`: Roles with `isActive === true`.
    - `systemRoles`: Roles with `isSystem === true`.
    - `customRoles`: Roles with `isSystem === false`.
    - `totalUsersWithRoles`: Count of active users with at least 1 assigned role.
    - `totalRegisteredPermissions`: Count of distinct actions in catalogue.
    - `averagePermissionsPerRole`: Mean number of permissions configured.
  - `GET /api/v1/roles/analytics`: Aggregates:
    - `userDistribution`: Count of staff assigned to each role.
    - `moduleCoverage`: Breakdown of granted permissions per module across roles.
    - `systemVsCustomRatio`: Headcount and percentage breakdown.
- [ ] **Task 4: Security Hardening & Privilege Escalation Defenses (`role.service.js`)**:
  - Block renaming or altering `isSystem` flag on core system roles (`HTTP 400 Bad Request`).
  - Block deleting `isSystem: true` roles (`HTTP 400 Bad Request`).
  - Block deleting or deactivating any custom role currently assigned to $\ge 1$ active user (`HTTP 409 Conflict`), requiring reassignment first.
  - Prevent privilege escalation in `assignUserRoles`: Actor cannot assign the `Super Admin` role unless actor is already Super Admin. Actor cannot grant any role that includes permissions the actor does not hold.
- [ ] **Task 5: Role Cloning & Parameter Validation**:
  - Validate `roleIdParamSchema` on all parameterized endpoints (`/:id`, `/:id/clone`).
  - Implement `cloneRole` service method ensuring all permissions, scopes, and limits duplicate cleanly into a new custom role with `isSystem: false`.

## Verification & Acceptance Criteria
